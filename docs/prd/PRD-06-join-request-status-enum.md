# PRD-06: Единый владелец словаря статусов join-заявок

- **Статус**: Draft
- **Приоритет**: P3 (Speculative)
- **Зависимости**: нет. Можно параллельно с любым PRD (пересечение с PRD-03
  тривиально разрешается ребейзом: меняются 3-4 строки).
- **Источник**: Architecture review 2026-07-09, кандидат 6

## Контекст

Словарь статусов join-заявки — `pending / declined / expired` — продублирован
в трёх слоях без единого владельца. Добавление статуса (например, `approved`)
требует синхронной правки трёх файлов, и ничто не поймает рассинхрон.

## Текущее состояние (доказательства)

1. **Схема БД**: CHECK-констрейнт
   `CONSTRAINT ck_join_requests_status CHECK (status IN ('pending','declined','expired'))`
   — `app/models.py:73`; плюс литерал `'pending'` как DEFAULT (`:69`) и в UPSERT
   (`models.py:396,402`).
2. **Веб-валидация**: `if status and status not in {"pending", "declined", "expired"}`
   — `app/web/routes.py:408`.
3. **Хендлер**: голые строки `"declined"` и `"expired"` при
   `mark_join_requests_status(...)` — `app/bot/handlers.py:229,235`;
   плюс `'pending'` в запросе `get_pending_fresh_join_requests` (`models.py:419`).

## Цель

Один модуль-владелец словаря статусов; схема, веб-валидация и хендлеры ссылаются
на него. Дрейф между Python-словарём и CHECK-констрейнтом БД ловится тестом.

## Целевой интерфейс (предложение; детали — на усмотрение исполнителя)

```python
# app/join_request_status.py  (или внутри модуля join-заявок после PRD-03)
from enum import StrEnum

class JoinRequestStatus(StrEnum):
    PENDING = "pending"
    DECLINED = "declined"
    EXPIRED = "expired"
```

Python 3.12 в проекте — `StrEnum` доступен; члены enum сравниваются со строками
и сериализуются в psycopg как строки без адаптеров.

## Функциональные требования

- **FR-1**: Появляется единственное определение словаря статусов (StrEnum или
  эквивалент).
- **FR-2**: Все Python-употребления строк-статусов заменяются ссылками на enum:
  `routes.py:408` (валидация — `status in JoinRequestStatus`),
  `handlers.py:229,235`, параметр `status` в `get_join_requests`,
  литерал в `get_pending_fresh_join_requests`.
- **FR-3**: DDL привязывается к enum одним из двух способов (на выбор исполнителя):
  - (а) список в CHECK-констрейнте и DEFAULT генерируются из enum при сборке
    `CREATE_TABLES_SQL` (значения enum — свои константы, не пользовательский ввод);
  - (б) DDL остаётся литеральным, но добавляется тест, который читает допустимые
    значения констрейнта из `information_schema` / `pg_constraint` и сравнивает
    с множеством значений enum — дрейф валит тест.
- **FR-4**: Строковые значения в БД не меняются: `'pending'`, `'declined'`,
  `'expired'` — существующие данные валидны без миграции.

## Инварианты (нельзя сломать)

1. UPSERT join-заявки сбрасывает статус в `pending` при повторной заявке
   (`models.py:397-402`).
2. API `/api/chats/{id}/join-requests?status=...` отвечает 400 на неизвестный
   статус (`routes.py:408-409`).
3. Существующие строки таблицы `join_requests` остаются валидными.

## Требования к тестам

- **T-1**: Все существующие тесты проходят (в т.ч. glue-тест джобы отклонения заявок).
- **T-2**: Тест синхронизации enum ↔ CHECK-констрейнт (обязателен при FR-3(б),
  желателен при FR-3(а)): множества значений совпадают.
- **T-3**: Тест: `mark_join_requests_status` с членом enum записывает ожидаемую
  строку в БД.

## Критерии приёмки

- [ ] `python -m pytest` — зелёный.
- [ ] `rg '"declined"|"expired"' app/ --type py` — вхождения только в модуле-владельце
      словаря (и в DDL, если выбран вариант FR-3(б)).
- [ ] `rg '"pending"' app/ --type py` — аналогично.
- [ ] Тест дрейфа enum ↔ БД существует и падает при рассинхроне (проверить,
      временно добавив значение в enum).

## Вне объёма

- Новые статусы (например, `approved`) — этот PRD только концентрирует словарь.
- Статусная машина / валидация переходов между статусами.
- Аналогичная работа для `message_type` (тот же паттерн, но словарь стабилен
  и живёт в одном модуле — отдельная задача при необходимости).
