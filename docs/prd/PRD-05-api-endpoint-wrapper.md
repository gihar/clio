# PRD-05: Единая обёртка API-эндпоинтов веб-админки

- **Статус**: Draft
- **Приоритет**: P2 (Worth exploring)
- **Зависимости**: желательно после PRD-02 (обёртка опирается на стабильную форму
  `{success, ...}` от сервисов). Можно параллельно с PRD-03/PRD-04/PRD-06.
- **Источник**: Architecture review 2026-07-09, кандидат 5

## Контекст

В `app/web/routes.py` (554 строки) девять API-хендлеров повторяют один и тот же
HTTP-каркас. Интерфейс каждого хендлера почти равен его реализации — мелкие модули
без глубины, а HTTP-политика (маппинг ошибок, guard'ы, сериализация) размазана
по всем девяти.

## Текущее состояние (доказательства)

Повторяющиеся блоки в `app/web/routes.py`:

- `try/except Exception → log → json_response({"error": str(e)}, 500)` —
  9 хендлеров: `:140-142, :162-164, :186-188, :219-221, :282-284, :312-314,
  :337-339, :362-364, :394-396, :426-428`.
- `except ValueError → 400 invalid chat_id` — 5 хендлеров:
  `:217, :280, :335, :360, :392, :424`.
- Guard `config.has_openrouter → 503 "OpenRouter API не настроен"` — 3 копии:
  `:323-328, :348-353, :373-378`.
- Маппинг `status = 200 if result["success"] else 400` — 3 копии: `:332, :357, :389`.
- Цикл сериализации datetime `msg["sent_at"] = msg["sent_at"].isoformat()` —
  3 копии: `:179-183, :204-208, :263-267` (плюс join-requests `:412-416`);
  при этом словари мутируются на месте.

Смежная утечка: `health_check` пишет SQL (`SELECT 1`) прямо в веб-модуле
(`routes.py:106-108`) — веб-слой лезет за seam персистентности.

## Цель

Одна глубокая обёртка эндпоинта, за которой спрятана вся HTTP-политика:
маппинг исключений в статусы, guard OpenRouter, маппинг `{success}` → статус,
сериализация datetime. Хендлеры сжимаются до «распарсить параметры → позвать
модуль → вернуть данные».

## Целевой интерфейс (предложение; детали — на усмотрение исполнителя)

Новый модуль `app/web/api_wrapper.py` (имя на усмотрение исполнителя):

```python
def api_endpoint(*, requires_llm: bool = False):
    """Декоратор API-хендлера. Владеет всей HTTP-политикой:

    - ValueError из хендлера           -> 400 {"error": ...}
    - любое другое исключение          -> log + 500 {"error": str(e)}
    - requires_llm и нет OpenRouter    -> 503 {"success": False, "error": "OpenRouter API не настроен"}
    - хендлер вернул dict с "success"  -> 200/400 по значению
    - хендлер вернул (data, status)    -> как указано
    - хендлер вернул data              -> 200
    - datetime в данных                -> .isoformat() (рекурсивно, без мутации входа)
    """
```

Сериализатор datetime — чистая функция «данные → новые данные» (не мутировать
словари, пришедшие из модулей чтения). `require_auth` остаётся отдельным
декоратором как есть (`routes.py:87`).

## Функциональные требования

- **FR-1**: Все девять API-хендлеров переводятся на обёртку; ручные try/except,
  guard'ы 503, маппинг `success→статус` и циклы `.isoformat()` из тел хендлеров
  удаляются.
- **FR-2**: Поведенческий паритет по каждому эндпоинту: те же статусы и те же
  JSON-тела во всех ветках, что и сейчас, включая специфичные 400-ответы
  валидации (`:199, :232-253` — параметры дат) и 404 «chat not found» (`:258`).
  Специфичная валидация остаётся в хендлерах — обёртка её не поглощает.
- **FR-3**: Логирование ошибок сохраняется с контекстом (имя эндпоинта в сообщении).
- **FR-4**: Сериализация не мутирует входные структуры — строит новые
  (стиль репозитория: immutability).
- **FR-5** (опционально, +): убрать SQL из `health_check`: в `app/database.py`
  появляется `async def ping() -> bool`, `health_check` вызывает его. 
- **FR-6** (опционально): если `routes.py` после рефакторинга всё ещё > 400 строк —
  допустимо разнести на `api_routes.py` / `pages.py` / `app.py` (фабрика),
  чистой релокацией.

## Инварианты (нельзя сломать)

1. Формы JSON-ответов и статусы всех эндпоинтов идентичны текущим (их читает
   фронтенд в `templates/*.html`).
2. CORS-middleware и Basic-auth работают как раньше; порядок декораторов
   не ломает `require_auth`.
3. `json_response` продолжает отдавать кириллицу без экранирования
   (`ensure_ascii=False`, `routes.py:58-64`).

## Требования к тестам

Это первые тесты веб-слоя. Использовать `aiohttp.test_utils` (идёт с aiohttp,
новых зависимостей нет); модули данных подменяются фейками — Postgres не нужен.

- **T-1**: Unit-тесты обёртки: исключение → 500 (+запись в лог); ValueError → 400;
  `requires_llm` без ключа → 503 с точным телом; dict c `success: False` → 400;
  `success: True` → 200; datetime → isoformat; вход не мутируется.
- **T-2**: Smoke через test client минимум для одного эндпоинта каждой категории
  (простой — `/api/stats`; LLM — `/api/chats/{id}/summary`): статус и форма тела.
- **T-3**: Существующие тесты проходят без изменений.

## Критерии приёмки

- [ ] `python -m pytest` — зелёный, есть новые тесты веб-слоя.
- [ ] `rg -c "status=500" app/web/routes.py` — 0 вхождений в телах хендлеров
      (вся политика — в обёртке).
- [ ] `rg -c "has_openrouter" app/web/` — ровно 1 вхождение (в обёртке).
- [ ] `rg "isoformat" app/web/routes.py` — 0 вхождений (сериализация — в обёртке).
- [ ] Каждый API-хендлер ≤ ~15 строк тела.
- [ ] Ответы эндпоинтов побайтово совпадают на happy-path (ручная проверка curl
      или smoke-тесты T-2).

## Вне объёма

- Изменение API-контрактов, версионирование, OpenAPI.
- Rate limiting (упомянут в CLAUDE.md как продакшен-соображение — отдельная задача).
- HTML-страницы (`dashboard`, `chats_page`, ...) — обёртка только для JSON-API.
- Правка доменного правила «вайбкод» в `chat_messages_page` (`routes.py:472-476`) —
  зафиксировано как мелкая фрикция, отдельная задача.
